# GitLab Workstation · GitLab 工作台

一个紧凑的持久化 DSH Bundle：在左侧栏添加 **GitLab 工作台** 页面，集中处理 GitLab 任务与 DSH 会话。Host 通过 `glab` **自动处理 Todo 评论提及**，同时支持**手动处理指派给我的开放 Issue**，并跟踪执行、闭环与人工接手。不需要 Python 或外置轮询脚本。

仓库：[lifeipkg/dsh-gitlab-workstation](https://github.com/lifeipkg/dsh-gitlab-workstation)。这是原仓库的改名，保留原有 Git 历史，而不是另起一套插件。

## 紧凑工作台（v2.33）

- **任务与环境分区**：收件箱、Todo、Issue、已处理属于任务视图；工作区与日志属于环境视图。不增加大卡片首页，直接进入任务列表。
- **上下文操作**：Todo 自动处理开关、模型选择与检查操作明确属于 Todo；Issue 保持手动处理，独立设置工作区、模型与思考强度。
- **信息密度优先**：紧凑状态条与列表行，任务状态、错误和人工接手入口优先；设置、回复预览及高级选项按需展开。
- **交互护栏**：不可逆操作保留两步确认；设置与路由弹层关闭后，旧请求不会关闭新开的草稿或弹层。关闭界面不撤销已经发送的保存/路由请求；被搜索隐藏的路由目标不能提交。
- **包身份同步**：npm 包名、加载包名及客户端模块 ID 已统一为 `@lifeipkg/dsh-gitlab-workstation`。旧 Loader 条目 ID、Bridge 路径和 `~/.dsh-plugins/gitlabtodo/state.json` 继续保留，以复用原任务与会话历史；这不是旧 npm 包的透明升级，须按下面说明显式切换，不可同时加载新旧消费者。

## 安装（分享给其他人）

前置条件（每个使用者各自准备）：

1. 安装 [GitLab CLI](https://gitlab.com/gitlab-org/cli)（`glab`），并登录目标 GitLab：

   ```sh
   glab auth login --hostname gitlab.example.com
   ```

   令牌需要 `api` 权限（读写 Todo、读取 discussions、回复 note）。`glab` 支持多主机，但插件当前只使用 GitLab 工作目录及 `glab` 配置解析出的单一主机/身份，不提供多账号同时隔离；启用前确认该目录中的 `glab` 命令访问的是目标主机。插件不保存任何令牌，全部调用走 `glab` 自身的认证配置。
2. DSH 中至少注册了一个工作区（新会话需要落在某个工作区里）。
3. 平台不限：Windows / macOS / Linux 均可，只需 `glab` 在 PATH 中。

安装方式二选一：

- **npm 安装**（新包发布后使用 `@lifeipkg/dsh-gitlab-workstation`，scope 需 `access: public` 已在 `publishConfig` 配好）：通过 DSH 插件管理安装本包后重启 DSH。源代码改名并不等于已发布到 npm；未发布时使用下面的源码方式。
- **从源码安装**：克隆本仓库，把 `package.json` 所在目录作为 bundle 放入 DSH 插件目录（形如 `~/.dsh-plugins/gitlabtodo/bundle/`），重启 DSH。

**从旧包显式切换**：`package.json` 的 `name`、`cordis.patch.yml` 的 `name`、`client.js` 的模块 `id` 三处必须完全一致，本版本均为 `@lifeipkg/dsh-gitlab-workstation`。它与旧包 `@lifeipkg/dsh-gitlab-todo-agent` 是不同安装身份，不会自动替换旧 bundle。先暂停旧插件的自动轮询，妥善结束在途处理并确认无活动派发/写入，再备份原配置与状态（备份可能含敏感设置，不要提交仓库）。停用旧 bundle，并检查手工 insert 条目，重启卸载旧客户端模块代；不要只依靠相同 Loader row ID 判断可以并装。

**保留数据，不保留并行消费者**：不要删除整个 `~/.dsh-plugins/gitlabtodo/` 数据目录；保留其中的 `state.json`。新包沿用原 `storageDirectory` 配置；若状态仍在旧包目录内的 `.runtime/state.json`，移除旧代码前先备份并显式核对 `legacyStateFile` 来源。本次改名不执行数据迁移。装好后确认只启用一份消费者，核对工作区、模型和轮询设置再启用；读入旧状态会保留原启用状态，不能假定新安装一定默认暂停。

历史说明：≤2.12.x 的 `@local/dsh-gitlab-todo-agent` 曾导致 `Cannot find package '@local/dsh-gitlab-todo-agent'`；同样须保留数据后显式移除旧加载条目并切换，不能删除父级状态目录来解决包名问题。

首次配置清单（装好后逐项确认再启用）：

1. 打开左侧 **GitLab 工作台** 页面。全新安装默认停用，不会立即创建任何 Session；旧版本升级保留原来的启用状态。
2. **设置** 中确认轮询间隔、每轮上限、自动处理并发数；Todo 视图内确认新会话使用的模型，可跟随 DSH 默认模型，也可固定为目录中的具体模型。
3. 可选：**Todo 新开会话的工作区**（留空跟随最近使用的工作区）、**预检模型**（轻量快速模型）。Issue 的工作区与模型在 Issue Tab 单独配置。
4. 可选：**Todo 会话附加规则**（见下节），把本团队工作区的专属约定注入 Todo 提示词；Issue 只发送链接和“开始处理”，由工作区 AGENTS.md／CLAUDE.md 提供规则。
5. 确认无误后启用轮询。

## 自定义附加规则（customRules）

不同团队的工作区规则差别很大（合并授权、专属流程文件、评审门槛……），插件内置的 Todo 会话提示词只保留通用条款：遵守工作区的 AGENTS.md／CLAUDE.md 与目标仓库规则、新 MR 的合并遵循既有规则、回复原 note、闭环结案报告等。Issue 面板不使用这套任务书，只发送 Issue 链接与“开始处理”。

内置条款还包括两条安全护栏，任何部署都生效：

- **危险操作护栏（默认只读 + 写操作白名单）**：会话由插件轮询 Todo 自动触发，原 note 及其讨论串是唯一授权依据。写操作只允许四类：回复讨论串/发表说明评论、标记本次处理覆盖的 Todo 完成、新建/更新自己的分支与 MR、提示词或附加规则明确豁免的自建 MR 合并；其余（触发/重试流水线与部署任务如 `rebuild_dev`、合并/关闭/approve 他人 MR、强推、删分支/标签、改项目设置、改指派/里程碑等）都必须有授权。授权必须是相关人员在讨论串中的**明确祈使或同意**并与操作逐字对应，疑问、玩笑、转述、模糊表态都不算。流水线红等问题只记录汇报，绝不主动触发或修复。附加规则可加严细化，但不得解除护栏。
- **工作范围**：只做原 note（及讨论串随后明确要求）的事；顺带发现的问题写进回复供人决策，不扩大范围；判定为"仅被提及"时不回复不干活，直接结案。

如果你的 Todo 工作区有更具体的要求，把它写进设置里的 **Todo 会话附加规则**（多行文本，上限 4000 字符）。该文本会作为第 9 条追加到每个 Todo 会话提示词末尾，并声明与其他条款冲突时优先适用。例如某个工作区允许"CI 全绿即可自行合并本会话新建的 MR"：

```text
- MR 合并豁免：本次处理新建的 MR（由本 Session 创建，或“插件记录的前序 MR”清单内的 MR）CI 全部通过后直接合并，无需人类授权；CI 未通过时先修复再重跑，仍失败则保留 MR 并说明原因。除此之外的 MR 不适用本条。
```

留空即使用纯通用提示词。从 v3（≤2.12.x）升级上来的旧安装，会自动把此前内嵌的专属规则预填进该设置，行为不变；不需要时清空即可。

## 使用

1. 确保 `glab` 已登录且能访问目标 GitLab。
2. 打开左侧 **GitLab 工作台** 页面。全新安装默认停用；升级会保留已有启用状态。
3. 在 **设置** 中配置轮询间隔、每轮上限与自动处理并发数（默认 2）；也可直接用 Todo 视图的模型下拉选择新会话模型。确认后再启用自动轮询。
4. 状态栏下方通过 **收件箱 / Todo 列表 / Issue / 已处理 / 工作区 / Log** Tab 切换：各列表随面板统一滚动，带有 **评论中 @ 我** 标签的事项会进入自动处理范围；**已处理**（v2.29 起并入原「最近会话」）按活动时刻倒序展示全部处理记录（规则跳过、预检跳过、会话派发与投递中的 pending 都在列，不按业务结果排除记录；用户可主动搜索当前已加载范围，搜索不会查询尚未加载的历史），默认每页 50 条可加载更多——**有会话的记录**直接带「打开 Session」与「归档 / 取消归档」按钮（仍执行中的会话不可归档），**无会话的记录**（一般是规则/预检判定不需要处理）在行内显示判定理由与被折叠去向，预检结果在此透明可查；打开该 Tab 期间每 10 秒静默刷新已加载范围，点击标题回源 GitLab。
5. **Issue Tab（v2.31）**：展示 GitLab 上**指派给我的开放 Issue**（按需拉取，不在轮询循环里；打开 Tab 自动刷新一次，之后跟随快照轮询缓存）。页顶 **Issue 会话设置** 独立配置新会话的工作区与模型，修改立即保存，不受 Todo 设置影响；选择具体模型后，只有 Host 目录为该模型声明 `reasoning.efforts` 时才显示 **思考强度**，可留“提供方默认”或选择目录给出的实际档位。每条 Issue 只提供 **处理**；处理后已处理的行显示执行/闭环状态，并可点 **打开会话** 跳回，不提供手动路由入口。点击处理会新开主线会话，标题固定为 **仓库名 #Issue 编号**，消息仅为 **Issue URL + 开始处理**；项目规则由该工作区的 AGENTS.md／CLAUDE.md 提供，插件不附加 Todo 任务书、customRules 或署名规则。Issue 与 Todo 共用派发记录和投影（合成 id `issue-<projectId>-<iid>` 不撞真实 Todo 数字 id），但 Issue 只走手动，不占自动并发槽、不自动续办或重试；闭环只认 Issue 的真实关闭状态（API 查不到不结案，下轮重试）。Issue 已关闭或不再指派后，记录移到下方「已关闭或取消指派」区保留会话入口。
6. Todo 会话内的 Agent 只有在实际完成后，才会按提示调用 `POST /todos/:id/mark_as_done`；Issue 的处理动作由工作区规则指导，插件闭环核对其真实关闭状态。

**Log Tab（v2.32）**：显示运行时内存日志——**只进内存环形缓冲、不落盘**，新→旧，打开期间每 3 秒静默刷新。每行 `时间 [级别] 单行消息`，级别可筛「全部 / 警告及以上」，支持「清空日志」（两步确认，清空后留一条审计行）。内存有硬上限防无限增长：条数 ≤ `LOG_MAX_ENTRIES`(500) 与合计字符 ≤ `LOG_MAX_CHARS`(64KB) 双维度，任一超就从头部淘汰最旧（FIFO），单条 ≤ `LOG_MAX_LINE_CHARS`(500 字) 截断标注；被丢的条数记 dropped，面板以 `-N` 显示已丢弃条数，悬停可查看说明。写入入口统一 `this.logger.<level>()`：进缓冲 + 透传宿主日志（自动补 `[gitlab-todo-agent]` 前缀，业务消息不带前缀），消息格式为单行「<对象/动作>：<结果/细节>」。bridge 新增 `logs`（GET 投影 / POST `clear:true`）。

## Issue Leader（v2.34，可选托管）

Issue Tab 顶部提供折叠的 **Leader** 区域。创建独立 Leader 会话、选择它的模型，将需要管理的 Issue 会话逐条「托管」，再明确启动。默认关闭，不自动接管存量会话；「新建 Issue 默认托管」是独立的可选授权，仅对开启之后具有真实创建证明的新会话生效。它不把 Issue 改成 Todo 自动任务，不占 Todo 自动并发槽，也不改变 worker 的模型、工作区或项目规则。

- **集中了解进度**：启动时给 Leader 一次当前名册简报，此后根据有界日志增量和状态变化汇总，稳定状态不不断唤醒模型。Leader 能读取已纳管会话，明确下一步时向原会话发送原 Issue 范围内的续办建议；idle 不是继续理由，回合结束也不代表 Issue 已关闭。
- **拿不准交给你**：问题在 Leader 会话和托管列表汇总，只暂停对应 Issue，其他继续管理。你确认业务判断后，用该 Issue 的明确恢复入口重新允许推进。正式工具审批／原生问答仍由人类在真实会话入口处理，Leader 不代答、不解除权限护栏。
- **只管理明确选中的会话**：首版限 Issue Tab 当前关联的独立 worker，路由目标与新建人工接手会话不隐式接管。Leader 自身只拥有纳管读取、受控推进和汇报工具，不提供 shell、任意网络／会话操作、权限修改或审批代办。
- **可暂停和恢复**：可暂停全部托管或单个 Issue。重启后默认暂停，需要重新明确启动；worker 为冷会话时仍可观察，但不会自动激活或推进，需人类先在原入口恢复。忙碌、排队、审批／问答未决、归档、缺失、未知或过期证据都拒绝推进。
- **失败不重复操作**：管理记录、人工待办、游标和动作 outbox 单独保存在同一存储目录的 `leader.json`。严格保存后才投递；创建或投递结果不确定时保留记录、阻止自动重试，不因换 requestId、解除后重选而重复执行。损坏或未知版本的 Leader journal 只冻结此功能，不覆盖文件，也不影响原 Todo 工作台。

Leader 续办使用原生 Agent 的非人类消息来源和 idle maintenance 同步校验，不使用会被宿主记作人类输入的普通 `session/prompt`；它不会因此获得恢复 goal、代答问题或批准工具的权限。托管权限变更经原生 Connection RPC，仅接受当前真实浏览器 Peer；普通 HTTP bridge 只读 Leader 快照，不能用 JSON 自报人类授权。该机制沿用本机单用户 Host 的信任边界，不宣称隔离能够执行任意本地脚本或读取浏览器凭据的同用户全权限程序。

正常卸载会先停止托管、取消并清理 Leader 自有自动队列，等其停止执行后再解除工具限制；不会取消 workers。已加载路径在原生 `agent/created` awaited barrier 内先安装限制并清除旧自有通知。但 Leader 使用已保存的普通 preset，**插件完全未加载／被禁用时不存在这些 runtime 限制**。崩溃恢复后不要在停用插件或 Leader journal 不可读的状态直接恢复旧 Leader；先重新加载插件并修复可读 journal 建立隔离，或由人类核查并清理旧自动输入。这不是宿主级永久隔离 preset。

首版安全预算：每次启动最长 24 小时／最多 100 次唤醒，每个 Issue 最长 72 小时／最多 20 次推进；日志缺口和预算耗尽交人类核查，不无限循环。需要 DSH 已有 Agent、会话控制器与会话投影服务，以及 Cordis 4.1；缺失时明确不可用，不回退成伪人类投递。现成实现复用本插件的会话跟踪／严格创建 journal，以及 DSH 的 `Agent.runMaintenance`、限定工具作用域和日志 API，没有引入新的多 Agent 框架。

## 安全打开与人工接手（v2.33.1）

最低 DSH 版本为 `0.2.2-rc.3`：本修复依赖并核对了该版本的权威会话查询、客户端会话引用与归档确认接口。未核验的早期 rc 不再声明支持；宿主能力不可用时不做不安全导航。

收件箱、Todo、Issue（含已关闭或取消指派记录）、已处理和工作区中的会话入口统一核验宿主真实状态，不再直接用历史 ID 跳转：

- **正常存在**：确认会话可加载且未归档后打开；加载失败留在当前面板并显示原因。
- **已归档**：显式选择「恢复并打开」。取得恢复确认后，再核验存在、归档状态和客户端加载结果；恢复失败不导航。
- **明确不存在**：显示「原会话不存在（可能已删除）」，保留任务、GitLab 链接及已有回复记录。宿主没有删除墓碑，不能仅凭不存在断言其删除原因；会话不存在也不代表 Todo 完成或 Issue 关闭。
- **无法核验**：显示原因与重试入口；网络、权限、分页缺失或加载错误不算删除，不静默新建会话。

对于可追溯的任务记录，可以明确确认「新建接手会话」。它只创建空白人工会话，交接摘要供人查看/复制/发送，不自动启动模型任务、不重新派发、不占自动并发槽，也不覆盖原会话 ID。工作区中没有对应任务的失效会话不提供该任务接手动作。

接手记录单独持久化：关闭或刷新后，从原会话入口仍可查看已创建的接手会话与资料。已创建但模型设置或记录保存失败时，显示已知会话 ID，重试复用它；创建请求结果不确定时禁止再次创建，需先人工核查宿主。关闭弹层只停止后续界面操作，不承诺撤销已经发送的恢复或创建请求。

导航使用临时会话引用并检查实际加载状态；`openSession` 返回并不代表异步加载成功。已完成导航后发生的外部删除仍由宿主处理，没有宿主原子导航接口时不能保证阻止所有后续竞态。本修复不使用「我已处理」清理失效会话，也不会因此触发 GitLab 标记完成。

## 内置轮询与识别规则

Host 每次轮询先通过 `glab api user` 获取并缓存当前用户 ID，再使用只读的 `glab api -X GET todos` 分页读取当前用户的待办，每页 100 条、最多 20 页。响应由 Host 直接解析、校验和归一化。

只有同时满足以下条件的 Todo 才属于“他人在评论中 @ 我”（自动处理范围）：

- `action_name` 为 `directly_addressed`（@ 出现在评论开头）或 `mentioned`（@ 出现在评论正文中）：二者都是他人在评论里点名我，都会进入自动处理；是否真需要处理由预检与会话内的“仅被提及”判定把关。指派、评审请求和其他通知不属于此类。
- `target_url` 包含 `#note_<id>`：Todo 来源于评论，而不是 Issue/MR 描述。
- `author.id` 不等于当前用户 ID：排除自己在评论中 @ 自己产生的 Todo。

该规则不限制 Issue、WorkItem 或 MergeRequest。指派（`assigned`）按规则直接标记完成；评审请求和其他通知仅保留在列表中，不自动创建 Session。

## 分类与处理规则

- **符合条件的评论直接提及**：开启 Todo 自动轮询时，按每轮上限选取 Todo 进入分派队列，由后台队列逐条分派。**自动处理并发数**（默认 2，可设 1–10）限制的是**带有未结算自动任务的会话数量**：同一自动会话中的多条 Todo 只算一个槽，首条结算后仍有自动路由任务在跑时继续占槽；会话上的自动任务全部结算后才释放。手动点击“开 Session 处理/重新处理”或手动路由是显式人工动作，不占用也不受该上限约束。

### 预检跳过

开启 **开会话前轻量预判**（默认开启）后，自动分派在创建会话之前先用一次轻量判定（v2.28 起引擎可选 `precheckEngine`：auto/jev/llm，默认 auto 优先 Jev/System One 决策模型，不可用自动回退聊天模型批量判定；Jev 通道见下文分类器设置）判断该提及是否真的需要处理：纯感谢/客套、纯 +1 附和、无关闲聊、无需回应的通报、测试性提及等会被判定为不需要，此时直接执行 `mark_as_done` 并把 Todo 记为 **已跳过（无需处理）**，副标题显示判定理由，不创建任何会话。预检本身失败（无 llm 服务、路由不可用、超时、输出不可解析）时，该 Todo **本轮跳过**：既不标记完成也不开会话，留在待办列表等下一轮重试（连续失败会写日志告警）——对代发账号，误开会话公开回复比晚一轮处理更难收回；手动分派不经过预检，随时可以绕过。
- 页面状态栏显示 **自动会话运行中 x/上限** 与 **排队待分派** 数量；Todo 视图提供模型快捷下拉，改动立即保存，无需打开设置。
- **讨论串纪律（防复读回环）**：多方都接入了同类自动化助手时，回复遵守增量要求——只写新事实（新问题的答案、本回合完成的工作、相对上次回复的状态变化、对他人事实错误的更正），既定步骤/阻塞条件/触发方式用"同 #note_<id>"引用不复述；复核已有同值实读证据时直接引用而不重复 GET。可渲染的 @ 只用于"对方有只有其本人能做的具体动作"（一条回复至多 @ 一个行动人，同一请求不重复 @），抄送/知会一律用反引号写法，不给其他自动化账号派新 Todo。需要人工的动作在讨论串中只 @ 一次，之后本线程的无增量提及按"仅被提及"直接标记完成、不回帖，由人工完成后的 @ 单向唤起——避免多个自动化会话互相"复核对方的复核"形成复读回环。
- **符合条件的 MR 评论提及**：同样创建 Session，不再因为目标是 MR 而直接标记完成。
- **指派通知（assigned）**：Issue 或 MR 被指派给我只是知会，规则直接 `mark_as_done`，记录为 **已跳过（规则）**，理由“指派通知（Issue/MR 被指派给我）”；人工重新派发同样只标记完成，不开会话。
- **其他 MR**：不自动处理；人工点击“标记完成”时，插件执行 `glab api -X POST todos/:id/mark_as_done` 并记录为 `merge-request-done`。
- **其他类型或提及方式**：只保留在列表中，不自动处理；人工点击“开 Session 处理”时才创建 Session。
- 手动“立即检查”只刷新结果，不触发自动分派。
- 已接受的 Todo 可通过列表中的 **打开 Session** 进入对应会话；“重新处理”是显式人工动作。

## Session 处理后的回复与完成标记

每个处理提示词都会携带 Todo ID、原 note ID、目标 URL 和 note 作者，并明确要求：

1. 正常处理结束后，在原 note 所属的 discussion 中回复提出该 note 的人，说明处理结果、实际改动或阻塞原因，而不是只新建顶层评论。
2. 只有实际完成该 Todo 后，才运行 `glab api -X POST todos/<todo-id>/mark_as_done`，仅标记当前这一条 Todo。
3. 无法完成、需要人类决策或未获发布授权时，不运行完成命令；正常情况下仍应在原 note 回应进度和阻塞原因。

## 闭环机制

插件会话是无人值守的单回合任务：新开会话在回合结束后结算；路由到已有会话时，每条 Todo 消息也独立结算，不要求目标会话关闭。闭环靠三件事保证。

**一、提示词里的运行环境**。每条 Todo 都按无人值守的单回合任务处理：没有人会回答提问；会话会被告知其 GitLab 账号（讨论串里该账号的 note 就是我方此前的回复）、会话标题、当前时间、第几轮和最多几轮、等待 CI 的预算（约 20 分钟）、闭环判定方式以及未闭环后的安排。最后必须输出带 `todoId` 的结案报告；共享回合处理多条路由任务时逐条并列输出：

```text
[TODO-CLOSURE] {"todoId":"当前 Todo ID","status":"done|waiting|needs-human","summary":"一句话结论","resumeAfterMinutes":30,"openMrs":["未合并 MR 链接"]}
```

**二、回合结束后核对事实**。回合结束只说明会话停了。插件随即重新拉取待办列表并读取原 note 的讨论串，以事实为准下结论，会话自述只作参考：

| 核对结果 | 结论 | 后续 |
|---|---|---|
| Todo 已标记完成，且讨论串里没有发现缺回复 | 已闭环 | 归档 |
| 自述 `needs-human`，且没有确认缺回复 | 需人工 | 不续办、不归档；即使 Todo 已消失也保留到人工确认 |
| 自述 `waiting` | 待续办 | 按 `resumeAfterMinutes` 续办；未给出时用设置的等待时间，逐轮翻倍 |
| 回合失败、漏回复、漏标记、没有结案报告 | 待续办 | 2、4、8… 分钟后续办补救 |
| 应续办但不允许（手动派发、开关关闭、轮数用尽、首轮派发已超 72 小时） | 需人工 | 同上 |

讨论串核对只支持项目级 Issue、WorkItem 和 MR；接口失败或找不到讨论串时按未知处理，不会因此判定缺回复。

**三、续办会话**。到期后插件新开一个会话（标题加 `-续N`），提示词带上前序各轮的结论、插件记录的未合并 MR 清单（来自会话自述、**未经插件核实**，合并前会话必须先读取 MR 详情核实 author 确为我方账号，核实不通过一律不合并）以及“上一轮缺回复”的提示。续办会话看不到前序会话的上下文，交接靠原 note 讨论串里的回复，所以回复必须写清 MR 清单、阻塞原因和等待条件。续办占用并发槽；同一 Issue/MR 上有其他插件会话在跑时顺延。

**需人工之后怎么接回来**。会话会在回复里点名需要谁做什么，并说明在讨论串提及我方账号即可继续。对方回复并 @ 后产生新 Todo，新会话的提示词会列出同一对象上遗留的未闭环 Todo 和它们的 MR，处理覆盖到的会一并标记完成。非需人工记录在 Todo 从待办列表消失后，下一轮轮询记为已闭环并归档会话；Todo 的需人工记录不会被这一规则自动关闭，即使 Todo 已消失也继续留在收件箱，直到人点击 **我已处理** 明确确认后才闭环并按设置归档。若会话在 `follow-up` 阶段已经归档，后续转需人工时会真实调用取消归档；取消失败保留真实状态和错误，下轮重试。

**重启中断**。状态停在“执行中”但已无人跟踪的会话，启动后会被接管结算；会话空闲且约 2 分钟内没有回合结束记录的，按中断处理并进入上面的核对。

**轮数预算**：`maxFollowUps`（默认 3）只计**补救轮**（回合失败、漏回复、漏标记）；纯等待外部条件的轮次（自述 `waiting`、回合正常、无缺回复）不消耗预算，只受 72 小时总时限约束。等待间隔以会话建议的 `resumeAfterMinutes` 为首选，但不低于逐轮翻倍的退避下限，避免会话把节奏固定死。续办会话创建连续失败时按 5、10、20、40 分钟退避，连续 5 次失败或链路超过 72 小时则升级为“需人工”进入收件箱，不再无限重试。流水线停在 `manual`（等待人工触发）不算事件，不会提前续办。

设置项：自动续办开关（默认开）、每条 Todo 最多自动补救轮数（默认 3）、续办等待时间（默认 15 分钟）。

**续办省 token（v2.20）**：

- **等待探测**（`waitProbeEnabled`，默认开）：到期的“纯等待”续办（上一轮自述 `waiting`、回合正常、无缺回复证据）不再直接开会话，而是先用 glab 看一眼——监视的 MR 没有状态翻转、原讨论串里我方最后一条回复之后也没有他人新回应，就把续办顺延一个等待周期，不消耗任何模型调用。任何不确定（读取失败、监视器还没有观测、补救类续办、MR 事件已触发）一律放行；连续推迟 4 次后放行一次心跳会话。
- **会话复用**（`followUpReuseSession`，默认开）：补救类与有变化的续办优先接力上一轮的同一个会话（已归档的先取消归档），沿用已有上下文、命中前缀缓存；会话已不存在、仍在执行、上一回合异常结束、挂有其他未结算任务，或已被接力 2 次时，退回“新开会话 + 摘要交接”。复用回合的提示词会明确告知“上下文仍在，但外部状态必须重新核实”。
- 以上两项都只影响续办，首轮派发不变；总时限（72 小时）与补救轮数预算照旧。

## DSH 会话交互（对齐 dsh-task-board 实现）

插件与 DSH 的全部会话操作都经 **typertGateway** 以 Host 本地 owner peer 调用（`session/modelCatalog|create|rename|selectModel|prompt|list|page` 与流式 `session/follow`），不使用浏览器传入的身份，与 [dsh-task-board](https://github.com/zhu1090093659/dsh-web/tree/main/packages/dsh-task-board) 的 HostExecutionRunner 同一调用契约。

**执行结算**：prompt 入队只代表“已接受”，不是完成。Host 定期（默认 3 秒，仅在有运行中会话或排队任务时轮询）读取会话名册：`running=true` 仍在执行；空闲后经 `session/follow` 开场帧与 `session/page` 有界回翻。新会话按本次启动后的 `turn/end` 结算；路由消息按 prompt `requestId` 在持久化 `user/message.source.rpcId` 中的位置定位自己的回合，因此同一会话可挂多条 Todo 并分别结算。结案报告必须带 `todoId`：即使 `steer` 与前序工作共用同一 `turn/end`，报告也不会串到别的 Todo；旧格式无 `todoId` 的报告只归因到下一条插件消息之前。只有对应 `turn/end.data.reason.kind === 'completed'` 才记为执行完成，其余（error/interrupted/max-tokens 等）记为执行失败；名册读取失败一律视为“仍在执行”，绝不误判为空闲。连续 24 轮读不到历史才按失败收口，避免永久占用。

**自动归档**：开启自动归档（默认开启）时，插件创建的会话在回合成功结束、且闭环核对结论为“已闭环”或“待续办”后，调用 `workspace/archiveSession` 归档（不带 `stopActivity`，仍有工作在跑会被 Host 拒绝并记录原因，绝不强行停止）。结论为“需人工”的 Todo 会话保留不归档，等人在收件箱明确点击“我已处理”后再归档；Issue 仍在实际关闭后闭环归档。**路由到已有会话的消息不会让插件归档这个目标会话**；插件创建的原会话若还挂着其他路由任务，也会等任务结算后再归档。手动“归档/取消归档”同样只接受插件创建过的会话。归档失败或被拒不影响执行结算；失败的会话不自动归档，保留供人工查看；可在设置中关闭。

**并发槽位**：并发按“有未结算自动任务的会话”计数。一个自动会话无论挂多少条 Todo 都只占一个槽；首条 Todo 结算不会提前释放，最后一条自动任务结算后才释放。手动新开或手动路由不计入也不受上限约束，但执行中禁止再次重新处理同一 Todo。

## 会话路由（v2.17）

- **手动路由**：Todo 行的“路由到会话”打开会话选择器，可按标题、会话 ID、工作目录搜索；候选显示运行状态、当前负载和“同一目标”标记。确认后直接向该会话 `session/prompt`，不再创建、重命名或改模型。
- **路由范围**：`plugin`（默认）只允许插件创建过的会话；`any` 可选手动打开的其他顶层会话。空白、子代理和已归档会话始终排除。仅被路由过的外部会话不会因此变成“插件创建”。
- **同目标自动续**：`autoRoute` 默认开启。自动派发时，如果同一 MR/Issue/WorkItem（去掉 `#note_` 锚点后 URL 相同）有最近 7 天内接受、未归档且负载未满的插件会话，新 Todo 直接追加给它，复用已有上下文；没有合适目标才新开会话。手动“开 Session 处理”不受影响，始终按原语义新建。
- **忙碌投递方式**：`busyRouteMode=queue`（默认）在当前回合结束后处理；`steer` 在当前回合的最近步骤边界插入引导，与前序工作共用该回合。目标空闲时两种方式都会直接开始新回合，插件统一使用 `queue`。
- **单会话负载上限**：`maxQueuePerSession` 默认 3（1–10），统计该会话尚未结算的 Todo 消息；达到上限后自动路由退回新会话，手动路由明确报错，避免把任务堆进长会话后无人察觉。
- **配置继承**：路由不改目标会话标题、模型、工作区或预设。危险操作护栏、原 note 回复、Todo 完成标记、结案报告与闭环核对全部照旧。
- **失败重试**：路由 pending 记录保存目标与 `requestId`，重试复用同一标识，由 Host 幂等去重；pending 未结算前禁止改投其他会话或另开会话，避免双执行。自动 pending 在后续轮询中跳过二次预检、直接重试，手动 pending 等人工重试。

## 收件箱、晨报与回复预览（v2.18）

- **需人工收件箱**：面板第一个 Tab。所有闭环结论为“需人工”且尚未确认的 Todo 集中列出，卡片给出原因（closureNote）、轮次、会话名与“旧消息未确认”标记，并提供两个动作：**打开会话接手**（直接跳到对应 DSH 会话继续做）与**我已处理**（把 Todo 标记完成、记录确认时间、闭环并按设置归档会话；标记失败不阻塞确认，原因写入结论）。
- **晨报卡片**：面板顶部“过去 24 小时”摘要——结算总数与闭环/待续办/需人工分布、当前仍待处理的开环数量，展开后逐条列出每条记录的一句话结论与我方回复节选（可直达回复 note）。
- **回复预览**：闭环核对时会捕获本轮我方账号发到原讨论串的最新回复正文快照（`lastReply`），Todo 列表、最近会话与收件箱卡片均可展开查看——不用再去 GitLab 翻“以我名义说了什么”。快照正文限长 2000 字符，本轮没有新回复时保留上一轮的快照。

## 批量预检（v2.18）

- **批量预检**：同一轮的新提及不再逐条调用预检模型，而是一次把整批交给 judge，输出每条的 `needsProcessing`、`priority`、`duplicateOf` 与 `preferSession`。批量解析失败自动退回逐条预检；单条缺失的判定视为预检失败，该 Todo 本轮跳过、下一轮重试（不再“缺失即放行开会话”）。
- **重复折叠**：judge 判定同批中某条与另一条实质是同一请求（`duplicateOf`）时，重复项直接标记完成并注明“随主条目合并处理”，同时保留其作者与正文摘录——主条目会话的提示词会带出这些被折叠的提及，要求会话一并覆盖处理，发现其中含不同请求时必须逐条指出并报 `needs-human`；只有主条目开会话——**仅限同一目标对象（同 MR/Issue）内的重复**；跨讨论串的重复提问不折叠（两个线程都要有回复）。链式或互相指向的判定按保守处理：可能多开会话，绝不把仍需处理的请求折叠掉。
- **优先级排序**：`priority` 1（最优先，阻塞他人/生产问题）到 5，派发队列按优先级稳定排序，紧急事项先拿到并发槽。
- **路由 LLM 化**：批量预检提示词附带给定 Todo 的同目标插件会话摘要（标题、上次结论），judge 输出 `preferSession`：`reuse`（与那个会话上下文相关，适合并入）或 `new`（虽同对象但主题无关）。`new` 时跳过同目标自动路由直接新开会话；`reuse` 或缺省沿用现有规则（最新同目标会话优先，逐候选过宿主校验）。规则始终是兜底，LLM 只否决不复用，不会越权指定任意会话。

### 预检分类器（Jev，v2.28）

`precheckEngine` 选 `auto`/`jev` 时走 System One 决策模型：判定字段映射 `needsProcessing→noul`、跳过理由→`choice`（枚举固定文案）、`priority→score`（1–5 归一）、`preferSession→choice`（有同目标候选会话才问）、批内去重→同 `targetKey` 条目成对 `match`（same/different/unclear）。`P(needs)` 落入 0.35–0.65 不确定带的条目自动交给聊天模型复核，其余条目不再消耗聊天调用。

分类器通道按序探测、首个可用者生效：
1. 宿主 `llm.classify`（未来 DSH 版本把 pi 的 classifier 层挂进插件服务时自动启用，当前没有）；
2. PATH 上的 `jev` CLI（读 jevctl 凭证 `~/.config/jev/credentials.json`，支持 `-m/--model`、`-P/--provider` 与内置代理）；
3. `precheckClassifier` 配置的 System One HTTP 直连（`baseUrl` + Bearer key；内置 typesafe/openrouter 预设，自定义端可填任意兼容地址）。凭证解析：设置里的 `apiKey` → 环境变量（预设 `TYPESAFE_API_KEY`/`OPENROUTER_API_KEY`，自定义填 `apiKeyEnv`）→ jevctl 凭证文件。

## 事件驱动续办与回复署名（v2.18）

- **事件驱动续办**：闭环结论为“待续办”且会话自述 `waiting`、带有未合并 MR 时，插件建立监视器（每条记录至多 3 个 MR），此后每轮轮询读取这些 MR 的状态：流水线从运行中翻转为 success/failed/canceled、MR 被合并或关闭时，立即把续办提前到本轮（不必等定时间隔）。一次翻转只触发一次，触发后监视器清除、由下一轮会话按需重建；无流水线变化或 API 失败时定时续办照常兜底。
- **回复署名**：`replySignature` 开启后，新派发 Todo 会话的提示词要求每条以我方名义发出的 GitLab 回复末尾单独一行原样加上署名（默认“—— 由 AI 助手代复”，文本可改，最长 100 字符），让对方知道是 AI 代发。默认关闭；只影响之后派发的 Todo 提示词，不附加到 Issue 的极简消息。

## 归档删除与定时清理（待宿主支持）

当前核验的 DSH `0.2.2-rc.3` 不提供持久会话删除接口；归档不是删除，删除工作区注册也不会删除会话。因此本版本**未实现归档会话永久删除或定时删除**，不会添加无效删除按钮、直接删数据目录或把隐藏记录当作清理。

已确认的后续策略为：仅本插件创建的归档 Todo/Issue 会话，保留 7 天、每小时扫描、默认关闭并由用户明确开启；排除路由到已有会话、仍有工作、待人工接手与归属不明的记录。存量记录缺少可信归档时间时，保留期从首次可靠观察归档起计算，不能从任务接受/完成时间猜测。上述策略是待办，不是本版本可启用的设置；需要宿主先提供安全删除及可核验的归属、归档时间契约。

## 新会话配置

- **新开会话的工作区文件夹**：须为 DSH 已注册的工作区路径（经 `workspaceRegistry` 解析为 `workspaceId` 传给 `session/create`）；未命中会显式报错，留空使用最近使用的工作区，绝不落回 Host 进程目录。它与 **GitLab 工作目录** 相互独立。
- **Todo 新开会话使用的模型**：直接遍历 Host 模型目录返回的全部模型分组；创建 Session 后依次执行 `session/rename` 与 `selectModel({ provider, model })`，再提交提示词。Todo 标题形如 `TODO-issue-7-note-10`，按目标类型与 note ID 命名；新建续办会话保留 `-续N` 后缀。只影响新建的 Todo 会话，历史标题、路由目标与复用的已有会话不批量改名。旧 pending 恢复时沿用已知标题，缺失时尝试读取 Host 精确投影；仍未知则留空，不把新前缀虚构成原标题。新 pending 只在 rename 已确认后保存标题。选择具体模型（包括“固定当前默认模型”）会固定该路由，不随 DSH 默认模型变化。
- **Issue 新开会话配置**：`issueSessionCwd` 与 `issueSessionModel` 跟 Todo 的 `sessionCwd`／`sessionModel` 完全分开。Issue 标题固定为 `仓库名 #iid`，不带“协助”或续办后缀。选择支持思考强度的具体模型时，`selectModel` 额外携带所选 `reasoningEffort`；选择“提供方默认”则省略该字段，由 Host 按模型适配器默认值处理。没有 `reasoning` 元数据的模型不显示强度选项，也不会凭模型名称猜测档位。
- 设置保存在 `state.json`，不修改已接受的历史 Session。工作区只在创建时确定；pending Session 重试会复用原工作区，但会重新应用对应类型的当前模型配置。旧版本升级时把原有共享工作区／模型一次性复制为 Issue 初始值，之后两边独立修改；全新安装的 Issue 默认跟随 DSH 默认模型与最近工作区。

## 去重与失败恢复

- 空结果不创建 Session。
- 只有提示词入队成功后，Todo ID 才进入已处理记录（`executionStatus=running`），避免下一轮重复开会话。
- Session 已创建但提示词未入队时，记录 pending Session，下轮复用而不是重复创建。
- Host 重启后会从持久记录恢复仍在运行的会话监控，继续按回合结果结算。
- 每轮自动创建数量可设为 1–10；剩余新 Todo 留到后续轮次。

## Bridge 安全

页面通过同源 `/api/gitlab-todo-agent` 与 Host 通信，路由注册在 DSH `connection.fetch` 上。Connection 统一完成 Host/Origin 检查、签名 Cookie 认证和 Owner Peer 校验，插件不另开无认证端点，也不自行读取或保存浏览器凭据；响应禁止缓存。
